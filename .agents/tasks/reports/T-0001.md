## Known limitations

Open questions for the orchestrator or owner. None was resolved by guessing.

1. **Execution loop order versus the gate.** Step 6 runs `set-status review` on `develop` before step 7 merges the branch. The report lives only on the task branch until the merge, so the gate fails on `develop` at step 6: the file is not in that working tree. The task file requires the report to "already exist" and does not say where. I implemented the literal check against the working tree of the checkout running the command, and documented that in the README. The loop's step order or the place `set-status` runs may need a decision; I changed neither.
2. **`touches` omits `tests/`.** The task requires a test module under `tests/` but `touches` lists none. I added `tests/test_set_status_gate.py`. The orchestrator owns widening `touches` and should record it.
3. **`done` and the done-only rules.** The gate runs `validate_report` with the task as it stands before the transition, which is exactly what `report.py validate` does at that moment. The verify-line and touches rules apply only once the task's status is already `done`. So a transition to `done` succeeds with a `pending` verify line, and `report.py validate` then fails the same task. The task's non-goals bar changing `report.py`'s rules, so I did not simulate the target status. If the gate should apply the done rules on the transition, that is a follow-up.
4. A report whose frontmatter cannot be parsed raises `FrontmatterError`, which `task.py` already reports as `error: ...` with exit code 1. It is not covered by a test.
5. The independent verify has not run. The verify line stays `pending` for the orchestrator.

## Lessons learned

`Task.report_path` resolves from `_schema.REPORTS_DIR`, which derives from the script's own location. Tests can therefore exercise `task.py` safely by copying `scripts/` and `templates/` into `tmp_path` and running the copy, with no monkeypatching. `task.py new --no-publish` seeds a valid task file there without git.
