## Fix round

The owner decided the three open questions from the first round. All three are implemented; the loop order is unchanged.

1. **Gate versus loop order.** `report_problems` reads the report from the working tree. If the file is absent, `branch_report_text` lists `refs/heads` and `refs/remotes/origin`, keeps refs whose name matches `*/<ID>-*`, and runs `git show <ref>:.agents/tasks/reports/<ID>.md`. Local branches are tried first, then `origin/`, each in name order; the first branch holding the file wins. The content goes through the same `validate_report`. Errors name the source, for example `chore/T-0001-x:.agents/tasks/reports/T-0001.md`. A report in neither place is refused as before, with a message that now also names the branch pattern. A working-tree report always wins over a branch report. The lookup uses local refs only; it does not fetch, so an `origin/` branch must already be fetched.
2. **`done` transition.** `report_problems` takes a `target_status`. When it differs from the task's status, `validate_report` runs against a copy of the task carrying that status, so the done-only rules apply. No rule text or `validate` output changed. For `done` this evaluates: the verify line exists, starts with `passed` and names a commit; the summary does not call the verify pending or excepted. The touches rule runs only if the touches box is ticked and the task's merge commit is reachable from `HEAD` in the repo; before the merge there is none, and it is skipped, as `validate` skips it. It reads the merge commit's diff, not the report source, so it works the same for a branch report. `review`, `blocked` and `abandoned` behave as before and accept a `pending` verify line.
3. **Unparseable frontmatter.** Tested for all four gated statuses on a working-tree report, and for a branch report: exit code 1, stderr starts with `error:`, no traceback, status unchanged. Branch-sourced frontmatter errors are prefixed with the branch and path.

`touches` widening: `tests/test_set_status_gate.py` was outside T-0001's `touches`. The orchestrator widened it on `develop` for this round.

## Known limitations

- The independent verify has not run for the fix round. The verify line stays `pending` for the orchestrator.
- The branch lookup does not fetch. If the orchestrator has not fetched the task branch and it is not local, the gate refuses with the "no report" message.
- If a stale local branch and a newer `origin/` branch both match, the local one is read. A stale report then fails validation or passes with old content; fetch and fast-forward the local branch first.
- At `done`, before the merge commit exists, the touches rule is not evaluated. After the merge it is. `validate` has the same limit.

## Lessons learned

`Task.report_path` resolves from `_schema.REPORTS_DIR`, which derives from the script's own location. Tests can therefore exercise `task.py` safely by copying `scripts/` and `templates/` into `tmp_path` and running the copy, with no monkeypatching. `task.py new --no-publish` seeds a valid task file there without git. For branch tests, `git init` the same `tmp_path`, commit the report on a task branch, and strip `GIT_*` variables from the test's git calls. A `validate_report` rule that keys on `task.status` can be judged for a target status by passing a copy of the task with that status; no rule change is needed.
